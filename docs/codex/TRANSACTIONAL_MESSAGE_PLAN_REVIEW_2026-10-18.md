## 实施单元与验收

1. **事务基础**：新增可选 `ITransactionDB`，提供显式 SQL 事务连接；Core `pkg/persistence/message` 提供独立事务执行、调用方事务内消费防重、不可变事件/流水的批量发布确认。启动建表仍由应用 EnsureStorage 完成，工具不建表、不推断记录结构、不自行重放业务。
2. **示例收敛**：06 Supplier 使用统一消费事务入口；06/07 已有 Outbox 复用统一批量确认。保留旧 action 的逐条兼容路径，验证缺 ID、零 ID、重复 ID、已发布及整事务回滚。
3. **07 同步调度**：接回框架 adaptive worker，取消业务 ticker。候选批量 512、收集阈值 32、最长收集 20ms，保留原背压、可靠落盘、远端确认后清理本地及资源关闭约束。参数是否合适由实测决定。
4. **订单事件并发**：同订单统一 ordering key，不同订单显式有界并发；保留失败屏障、owner/reclaim 和 ACK。全局零值默认不变，不额外实现 pipeline 或另一套 worker。
5. **回归与测量**：保留 RED 证据；真实 SQLite 验证事务、业务行复用和重放；专用 MySQL/Redis 验证回滚及多进程正常、重复与恢复；受影响整包 race、兼容契约、日志及 skill 检查；真实负载区分接单、数据库、发布和消费组排空。长稳态、容量矩阵等未实际运行时明确记 NOT_RUN，不用短时数据替代。

### 长压发现的 MySQL 连接恢复缺陷

长窗首个 `unexpected EOF` / `invalid connection` 后出现大量 `sql: database is closed`。现有 `RemoveIfSame` 已防止旧实例删除新池，但原逻辑仍把单个物理连接失败升级为关闭整个共享池，并且旧 Clone 不会在新事务前重绑新池；Begin 失败也未清掉缓存中的已关闭池。这些错误可放大一次连接故障；尚不能把整段长窗失败都归因于此。

- `pool-recovery-red-r2.log`：固定旧源码 overlay 在真实专用 MySQL 上分别复现单物理连接失败关闭共享池、旧 Clone 开新事务使用已关闭池、Begin 失败留下关闭池，三个运行时 RED。首轮测试误引用新 helper 的编译失败单独保留，不冒充行为 RED。
- 当前恢复规则：物理连接由 MySQL 驱动回收，不关闭共享池；只有明确整池关闭才按同池身份驱逐。非事务只读保留一次恢复重试；新操作重绑当前池，活动事务保持原连接，写入和事务不自动重放。健康探测超时不得中断其他在途事务。
- `begin-recovery-red.log` 为新增 Begin 边界的当前实现 RED；修复保留错误原因并驱逐关闭池，后续由调用方显式开启新事务，不重跑失败业务。
