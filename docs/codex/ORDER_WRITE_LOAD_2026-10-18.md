### 前置项：补齐 Core 统一的事务消息持久化方案

用户指出 Outbox/Inbox 应为框架统一能力。核对当前代码后：Core 的 `pkg/server/event/outbox.go` 提供 OutboxStore 接口和统一发布器，`ServiceContext.UseOutbox` 负责运行时接入；可靠订阅和 Broker ACK/reclaim 也由 Core 管理。但持久化模型、查询、事务写入与发布状态更新仍由示例各自实现，`pkg/` 内未提供统一持久 Inbox 模型、Store 和消费事务入口。这是当前标准实现不完整的架构缺口，不能仅以“数据库可选”解释。

06 的 SQLite 与 07 的共享 MySQL 可以是统一存储适配方案下的不同后端；07 用 `sync.Map` 去重则只有进程内语义，不等价于持久 Inbox。07 已有的压测和 ACK 验收不覆盖持久 Inbox 崩溃事务恢复，也不能据此宣传完整事务消息能力已统一。

修订后统一 Core 的事务接入、SQL 持久化工具及发布/消费契约，复用现有发布器和订阅器，不强制独立 Outbox/Inbox 模型或额外建表。业务数据库连接/事务沿用应用自己的 MySQL/SQLite，记录可为独立消息记录或经使用者确认可复用的业务事实。事件、业务处理、稳定消费身份、ordering key、revision、记录复用和目标子状态都需按权威 skill 与使用者确认。消费幂等跨副本依靠持久唯一约束及事务，不靠进程 mutex 或内存 map。需要建表时仍由启动阶段 EnsureStorage 经框架执行。

发布侧由同一事务提交业务事实与 Outbox；消费侧由同一事务提交业务更新与 Inbox 完成记录，成功提交后才允许 Broker ACK。外部 HTTP/WebSocket 副作用不能被 SQL 事务自动覆盖，应使用幂等接收或再次写出可靠事件等明确边界，不承诺通用 exactly-once。采用 KV 时也必须证明业务事实和事件处于同一 KV 事务；不能把 MySQL 业务与独立 Badger Outbox/Inbox 的双写当成同事务。

各服务持有自己的数据边界，统一框架能力无需所有服务共用一套数据库或强制所有应用安装 MySQL。没有启用 MQ 时保留进程内事件中心能力；MQ 扩展跨进程传输，不应决定事务消息表的存储后端，也不应因接入框架自动引入 Redis/MQ 依赖。纯内存去重须明确标为非持久模式，不能作为可靠 Inbox 的默认替代。

06/07 先收敛到这套标准接入，再在 Core 标准实现中落地下面的批量确认与消费并发优化，避免在各应用中复制一轮可靠性和性能修复。现有 OutboxStore/UseOutbox 接口保持兼容；本项目前只是建议，尚未设计或实现新的公开 API，需单独验证存量数据和消费身份迁移。

| 路径 | 代价与适用范围 | 选择 |
| --- | --- | --- |
| 仅调大批量或缩短 ticker | 修改小，但重复扫描与串行消费仍存在，还可能增加事务/IO 压力 | 可作为对照实验，不作为完整方案 |
| 直接增加 order 副本 | 能分担本地接单/同步；共享 MySQL 与同一消费组 active owner 仍可能成为瓶颈 | 单副本问题明确后再做容量矩阵 |

### 使用 MQ 时的职责澄清

需要区分“完整消息的持久接收队列”和“与业务更新同事务的消费去重记录”：二者都可能被称为 Inbox，但并非同一种职责。前一轮把它们混在一起，使 SharedBadger 收发日志看起来是接入 MQ 后仍必须增加的一层，这不准确。

使用具备相应持久化、确认、重投和保留保证的 MQ 时，默认建议为：生产方业务事实与 Outbox 同事务；Core 将事件投递到 MQ，在 Broker 可靠接管后确认 Outbox；消费方在同一业务事务中提交业务变化和消费去重记录，成功后 ACK MQ。无需默认再复制一份完整消息到本地 Badger 队列，也无需等待消费方业务回执才确认生产方 Outbox。

Outbox 解决“业务数据库提交成功，进程在发布 MQ 前崩溃”的发送缺口；消费去重记录或等价业务幂等事实解决“业务提交成功，进程在 ACK MQ 前崩溃”的重复执行。MQ 的可靠投递不自动把应用数据库提交与 Publish/ACK 合并成一个原子操作，因此接入 MQ 后这些事务边界仍然存在。业务本身已有同事务、跨副本有效的幂等事实时，可复用该事实，不强制额外建立 Inbox 表。

下一节 SharedBadger 完整收发日志仅作为无 Broker 的可靠直投或明确需要提前接收、异步本地处理时的候选方案；并非已批准的默认方案。使用 MQ 时提前 ACK 并转存本地 Inbox 意味着恢复责任从 Broker 转移到本地卷，必须有明确收益与相应恢复保障，不能当作无条件可靠性增强。前置项的 SQL 标准事务接入与下一节候选日志不得未经决策叠加为两套强制队列。

### 待讨论的简化方案：业务记录主状态与按需投递明细

用户建议复用业务记录保存投递主状态，单目标不写子表，多目标按需保存子状态。该方案可以减少冗余写入，不要求所有消息都独立保存完整 Outbox 行；Core 应统一投递和幂等契约，并允许标准 Store 适配业务记录。此前“默认标准模型”建议不应被理解成强制所有应用额外写独立 Outbox/Inbox 表。本节为候选设计，未修改当前公开 API 或实现。

- **事件数量与投递目标数量是两个维度。** 单条不可变流水对应一个事件、一个目标时，可随业务提交投递状态，无需额外事件子表。一个事件有多个独立发布目标时，可增加按 EventID 和目标唯一的投递明细，主状态汇总完成度。但同一订单产生创建、支付、取消等多个必须保留的事件时，即使只有一个目标，也须有各自可恢复的事件身份、内容与状态；可复用已有业务流水，否则仍需事件明细。仅需最终状态同步时可明确合并中间版本，不能默默改变事件语义。
- **同事务保存投递意图。** 业务变化、对应事件版本的待投递状态，以及必要的目标明细/目标集合在同一业务事务内提交。事件内容应由不可变业务事实重建或保存快照，不能重试时随意使用已变化的当前业务值。
- **确认必须对应具体事件版本。** 更新发布状态应匹配 EventID/版本及目标，旧发布任务的确认不能覆盖刚产生的新版本 pending。多发布进程需有一致的领取、重试和幂等规则，不能因省去子表就依靠进程内锁。
- **MQ 扇出不等于生产方逐服务投递。** 一个事件只发布一次到一个 subject，再由多个逻辑消费组订阅时，生产方只需记录 Broker 发布确认，通常无需为每个消费服务增加子状态。只有生产方确实执行多个独立发布目标，才需对应投递明细。各消费者处理完成由自身消费组和幂等事实管理；若业务要求汇总下游完成进度，应作为独立业务流程或回执状态，不得与 Outbox published 混用。
- **目标集合与主状态含义必须明确。** 若采用多目标明细，明确本次事件的必需目标，主状态只能在这些目标均达到约定确认阶段后完成。重试只处理未确认目标。运行中新增订阅方不能使旧事件主状态含义自动改变；历史补投应显式安排。
- **Inbox 可以复用业务幂等事实。** 若消费方已有库存流水等记录，可用稳定消费身份及 EventID 的唯一约束与业务更新同事务防重，无需另写 Inbox。单个可变业务对象上的一个 processed 标记通常不足以覆盖多事件、多独立处理者；既有唯一业务键是否足够须按具体事件语义证明。

本方案需验证：单目标零额外事件行、多目标部分失败恢复、单订单多事件不覆盖、旧版本确认与新版本提交竞争、并发重复消费，以及一个 subject 多消费组不产生多余生产方目标明细。减少存储次数是候选收益，尚未实施或压测。

### 已排除的备选方案：以 SharedBadger 统一可靠消息收发日志

用户随后明确不采用此方案；以下仅保留讨论及技术边界，不属于本次实施范围。

用户提出所有服务使用 Core 内部 SharedBadger 保存 Outbox/Inbox：发送记录在接收方持久接收后删除；服务内从 Inbox 驱动处理，并把后续消息写入 Outbox。这个方向可以统一可靠传输和崩溃重试，也可减少应用自写消息存储。但这是对上一节 SQL 事务消息接入建议的另一种架构选择，尚未批准替换现行契约，不能只替换存储后端便宣称完成事务可靠性。

- **持久接收与业务完成分开确认。** 接收方先原子写入完整消息、稳定消费身份、EventID 和 pending 状态，满足持久化条件后返回接收回执；此时接收方承担恢复和重试责任，不表示业务成功。发送方只有收到匹配 EventID/目标的可靠回执后，才可删除对应投递记录；回执丢失则重投，接收方必须幂等返回。业务结果若需反馈，应定义另一个结果事件。持久接收后处理失败不得静默丢弃，应保持可观测重试或进入保留数据的失败状态。
- **当前发布确认不等于接收方回执。** 现行 `OutboxBatchMarker` 仅确认 MQ 发布，不代表消费者 Inbox 已落盘。若保留 Broker，需选择 Broker 在明确持久化/保留保证下接管消息，或另建应用接收回执协议；二者不能混用。多目标投递按稳定逻辑订阅方分别跟踪，一个接收方成功不能删除其他目标的未确认责任；同一消费组的实例不应被误当作不同订阅方。
- **本地事务必须覆盖完整状态转换。** 若业务事实也在同一 Badger 数据库，可设计同一事务提交业务变化、Inbox 完成标记及新 Outbox；起始请求同样要保证业务可靠记录与待发送事件原子提交。仅共享 manager/目录、依次调用不同 prefix 的 Save 不证明同事务。当前 `ApplyWriteOperations` 有事务过大拆批及已提交前缀语义，不能把任意大批量自动视为一个原子业务单元。超限的单个原子业务单元应拒绝或明确重新设计。
- **MySQL 业务不能因消息统一到 Badger 就免除事务接入。** SQL 已提交而 Badger 完成标记未提交时会重放；反向先标完成则可能漏做业务。需用业务权威库中的 EventID/消费身份幂等事实与业务更新同事务提交，并可靠记录待发输出，再可恢复地交接给本地消息日志；或由同一个本地可靠信封承载完整待应用业务与输出，配合远端事务幂等确认。后者需单独证明恢复和输出可见时机，现有通用 write-behind 不自动提供这些保证。HTTP/WebSocket 等外部副作用仍需自己的幂等/可靠交接契约。
- **Inbox 处理完成后不能立即抹掉全部去重依据。** 大消息体可以回收，完成回执/幂等事实须覆盖发送重试、Broker reclaim、人工重放及数据恢复窗口；无法界定窗口时，需保留持久业务唯一键、revision 等防重依据。业务拒绝和事务成功必须有明确终态，不能仅以记录不存在推导处理完成。
- **SharedBadger 是实例内共享，不是跨实例复制存储。** 持久卷需跟随实例恢复，并与稳定身份、旧 Boot 隔离、退出保护一致；多副本仍需服务级幂等和同 key 顺序设计。只剩接收方本地副本时，永久丢盘不在单机持久化保证内。若需覆盖节点/磁盘永久丢失，需复制存储或由可靠 Broker 继续保留恢复责任。
- **不能直接使用普通 shared 默认配置。** 当前 `DefaultSharedConfig` 为 `SyncWrites=false`，可靠消息接收确认须使用经验证的同步持久化配置。现有 `UseWriteBehind` 已拒绝非同步写、不检测冲突或非 fail 的损坏策略；新增消息日志也需显式落实同等级契约，并在磁盘满/写失败时停止成功确认。删除 key 与物理磁盘回收不是同一步，需配套容量背压和安全 GC。
- **统一可靠入口不要求所有内存事件都落盘。** 可将可靠异步链路规范为 Inbox → 业务处理 → Outbox；无后续事件的处理无需产生 Outbox。进程内普通事件仍由默认 EventCenter 工作，可靠持久化应有明确接入范围。MQ 可作为跨服务传输扩展；无 MQ 的跨服务可靠投递仍需明确网络传输和回执协议，不能从进程内事件中心推导已具备跨进程传输能力。

该方案的验收必须覆盖：落盘前崩溃、落盘后回执丢失、业务提交后本地标记前崩溃、输出写入/发送/确认各阶段崩溃、重复投递到不同副本、多订阅方部分确认、原卷恢复、旧 Boot、磁盘满与去重记录回收后重放。当前这些是设计约束及待运行项，不是 SharedBadger 统一收发实现已经存在或已经通过验证的声明。

### 1. 先统一 pending 调度，复用现有框架入口

07 当前 `AutoSync=false` 并另启 100ms 业务循环。改为显式配置现有自适应 worker：`AutoSync=true`，候选起点 `SyncBatchSize=512`、`SyncFlushThreshold=32`、`SyncMaxCollectDelay=20ms`、`SyncBacklogDrainDelay=0`；这些是待测参数，不是默认值变更或吞吐承诺。

移除重复的业务 ticker，由标准 `UseWriteBehind(OrderWriteBehindTarget)`、`ServiceContext.UseResource` 统一负责调度和资源关闭。当前 adaptive 构造器已在返回前初始化/恢复索引；正常 worker 调用队列处理，不逐批走 `ForceSyncBatch` 的全前缀重建。因此第一步可以同时避开固定等待和热路径重复扫描，不必先重写通用同步器。手动 `ForceSyncBatch` 的恢复语义需另外审查所有调用方，保持兼容，不能直接删去重建逻辑。

接入时在开始远程事务前保留服务准入检查；通用存储 worker 本身不知道 stable ServiceContext，不能只改 `AutoSync` 而遗漏门禁。已有 Outbox 周期扫描负责可靠兜底，`NotifyOutbox` 只是成功同步后的低延迟唤醒，不是数据可靠性条件。失败/零进展继续退避，恢复沿用原卷，关闭仍检查未确认 pending。

### 2. 再减少 Outbox 的数据库往返

当前 `MarkPublishedBatch` 已合并事务，但 `MarkOutboxPublishedByIDs` 内部仍逐条 Update。先对待处理点查、批量确认查询设置适当的 `SkipCount=true`，并在 models 当前 MySQL 事务内实现真正的有界批量状态更新，只更新 published、发布时间和必要元数据。先核对并锁定完整 ID 集合，保持空集合无事务、已发布幂等成功、缺失 ID 报错及整批回滚，不因优化跳过模型约束、元数据或审计语义。索引是否需要补充由实际执行计划决定，通过框架启动阶段 EnsureStorage 管理。

继续保留 earliest-first 加载、发布成功前缀确认与失败屏障。独立测量发布耗时和确认 SQL 成本后，再通过已有 `UseOutboxWithOptions` 评估分 key 并发；无需为了唤醒或并发新造另一套发布器。

### 3. 消费端按业务 key 并发，复用已有 keyed-reliable

为同一订单的创建/状态/支付事件统一提供稳定 ordering key，例如服务名与 OrderID 的组合；生产侧 Outbox 和 Broker 载荷保持一致。消费者先核对缓存失效、WebSocket 通知和去重处理的并发安全，再显式设置 `Subscription.KeyConcurrency`，依次测试 4、8，必要时才扩至 16。当前 Redis keyed 路径已有有界窗口批量读取和按 key 调度，同订单串行、不同订单并行；保持 owner、reclaim、ACK 及失败 key 隔离，不能把 subject 简单改成无界并发。

先验证现有 keyed 路径是否达到目标；若 owner/ACK 的网络往返仍占主导，再对 Broker 调用做有界批量或 pipeline 优化，先证明所有权检查及 ACK 的原子边界不变。数据库事务、Lua 和 handler 不能被任意合并来换吞吐。单发布实例的 KeyConcurrency 也不代表多个 publisher 间已获得同 key 全局顺序，多副本须单独验证。全局默认仍保持旧串行契约，应用显式启用。

### 4. 每一步独立对照，再做稳态和故障验收

每阶段保持相同业务与持久化参数，对比原始基线和上一阶段，采集三层队列、最旧待处理时间、延迟、SQL 次数、每批条数、CPU、RSS 和磁盘；至少重复 5 次再判断稳定收益。用 CPU profile/SQL 与 Broker 指标定量归因，不把代码中的结构性开销直接当成全部耗时。

最终建议验收为持续 2000 笔/秒 10 分钟：真实发送达到目标且发送器无丢弃，成功率至少 99.9%，已确认数据零丢失/错键，三层队列在稳态无持续增长，消费 lag 和 pending 均可排空。停载后 5 秒内各层排空作为首期目标，属于拟定验收目标，并非当前实测能力。保留本地 pending/磁盘背压；观测缺失或达到既有资源硬界时终止负载并记为未达标，不能提前结束窗口后宣称稳态通过。

再验证断网、重投/重复、同 key 顺序与 revision、失败 key 对其他 key 的隔离、硬崩溃原卷恢复、旧 Boot 与关闭保护，以及相关包 race/公开契约回归；最后才做 1/2/4 副本扩展测试。实际生产消费方升级另列迁移范围，本方案不隐式授权。
