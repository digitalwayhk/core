# Core v1.6.1：有界 write-behind 成功确认后的本地回收

## 版本与根因

兼容补丁，基线为 v1.6.0 / `827a9f840f57f5b68c6481a380c8973f6c8d1467`。独立修复提交 `b66056a56b8ddf976eca808a64b692813bb97074` 已快进合入本地 main；正式发布提交以 annotated tag `v1.6.1` 和 GitHub Release 为准，禁止重写旧 tag。

普通 `UseWriteBehind` 已在确认提交后调用本地删除 hook；有界 target 成功和应用显式 Confirm 原来只完成本地确认、移除 pending，却漏掉清理调度，因此出现 pending=0、hook 未调用、本地副本残留。本次只在 `processDispositionRound` / `applyDispositionDecision` 实际确认事务成功后，把原版本候选交给既有 `scheduleSyncAfterDelete`。确认事务内不调用 hook。

未修改公开 API、配置、持久状态格式、模块依赖、pending 计数、重试预算、失败历史、顺序屏障、普通同步路径、Redis Provider 或 WebSocket。不是业务数据丢失或 MySQL 性能修复。

## 消费方升级与边界

正式发布后锁定补丁版本：

```bash
go get github.com/digitalwayhk/core@v1.6.1
```

继续原 `UseWriteBehindWithFailureHandler`、target、应用 Confirm 和 `IsSyncAfterDelete`，无需新 worker 或接入 API。消费方须核对 hook 返回 true 的业务条件：修复后有界模式开始实际执行此条件，不能依赖原遗漏保留副本。hook=false 保留；同 key 后续版本必须在自己的成功确认后才可清理。旧回执、指纹冲突、确认事务失败、暂停、接管、Release 或迟到结果均不能借此删除新记录。

只回收本地模型副本，不触发远端 tombstone，不回收失败/完成历史。旧版已经确认的残留不会因升级自动补删；若需处置，须另行由应用认可，不能用 PurgeLocal、Delete、清 pending 或清历史绕过删除条件。

既有异步清理队列仅在内存：确认提交到清理完成之间退出，重启不自动补删，也不会因此重投已确认 target。pending=0、Close 成功和物理回收完成是不同事实。真实原卷关闭/重开测试保留这一边界，本次没有增加持久回收机制。

有界失败处置仍冻结原 StoreID/policy；禁止旧二进制直接打开不识别的新模式卷，禁止删标记迁移。此补丁没有改变原回滚合同。
