# v1.4.4：可靠事件跨实例分担与多实例演示

基于 v1.4.3 / `d26004683e5f3366bae54ccf627d52828dd1b4ce`，修复显式要求横向分担时异步事件仍集中在整主题 owner 的限制。保留 v1.4.2 的持续调度、有限 worker/预取及原有可靠投递契约，不删除 Stream、消费组、历史消息或游标。版本由用户明确确认采用 v1.4.4，不覆盖已发布 v1.4.3。

## 使用与升级

```bash
go get github.com/digitalwayhk/core@v1.4.4
```

业务继续用正式 `sc.SubscribeEvent`，共享逻辑服务 group 与稳定 ShardKey；显式配置 `SharedKeys:true`、每实例 `KeyConcurrency:N` 和组级 `Prefetch:W`。没有要求共享消费的旧零值继续单 owner，单用 KeyConcurrency 不代表跨实例能力。Redis 使用按 key 执行租约和原子 fenced ACK；NATS 未实现 ordered/keyed/shared，显式要求会拒绝。通用能力不暴露 Redis 锁、Stream key 或 Lua 给业务。

**启用共享模式前必须停止目标组的旧订阅、确认真实 handler 已退出并等待原 lease 释放。** 模式和有效 W 持久冻结；副本须配置一致有效 W。新进程恢复原 pending，再继续新消息，不清数据。旧版本/旧模式不能混跑共享组，不能直接退回旧 tag 继续消费。在线 Provider 切换、调 W 和 Shared→legacy 原地回退均未提供安全迁移工具，禁止删标记或重置组绕过。完整步骤见[根因、实现与验收](SHARED_KEY_RELIABLE_CONSUMPTION_2026-10-20.md)。

顺序只限同 subject/group/key 的 Broker 接收顺序，不保证不同 subject 的全局用户顺序。租约过期不意味着旧业务/远端调用已停止；旧 owner 不得有效 ACK/DLQ，但业务仍须用数据库事务幂等和版本约束保护跨副本副作用，保持 at-least-once。

## 第10个示例

[examples/10-reliable-multi-instance](../../examples/10-reliable-multi-instance) 提供一个发布服务与两个消费副本。直接运行标准 main 即可，不需要应用自写消费循环。用户可通过正式 Private API 提交慢任务、失败重试任务，分别读取两实例 PID、instanceID、本人进度和 MQ 指标。配套三服务真实 HTTP 测试复用标准进程、Token 与请求工具，覆盖匿名拒绝、伪造 UserID、用户隔离、两个 PID 分担、慢 key 与失败屏障。

该例没有业务数据库模型，本地进度有界且重启清空，不冒充持久 Inbox 或业务数据库事务 Outbox。发布成功只代表 Broker 接收。生产仍需按实际业务选择事务投递与幂等记录；示例生命周期阈值不是框架默认值。

## 验证证据

原始双进程 RED 在修改前真实运行：A1 未完成时另一进程 B1 无法完成；另有能力拒绝、模式准入竞态、指标、Prefetch 与 Provider 切换 RED。它们与 GREEN 分开保存，详细绑定见本地 `.temp/shared-keys-20261020/`。新旧行为均进入包测试，原 v1.4.2 cross-window 用例继续通过。

最终普通及 race 命令均退出 0；mq/event/observability 的该轮记录各有 234 个 pass、28 个 skip 事件（含包与子用例事件，不能当独立场景数）。另补的持续输入预算测试以 `-race -count=3` 通过，首轮使用错误指标名的夹具失败保留，不算框架 RED。原生硬崩溃 race 测试实际硬杀 PID 89034，PID 89035 等原生 lease 后接管，恢复约 1m59.997s，A1 完成后才 A2，其他 key 期间继续处理。三服务 HTTP 最终 race 验证两个消费 PID 69885/68628 均处理，测试约 84 秒（含三个服务构建/启动）；内部 gRPC 已显式绑定回环地址。受影响包及示例 vet 通过。最终包级普通/race 记录见 `after-review-packages`、`after-review-race`。

全仓根模块回归 `SHOP_REDIS_ADDR=<本轮专属Redis> GOWORK=off go test -p 1 ./... -count=1 -json -timeout=6m` 退出 0：134 个有测试结果的包通过，2566 个测试/子测试 pass 事件、195 个 skip 事件，不能将事件总数当成独立场景数。未配置外部 MySQL/etcd/NATS 和显式专项仍跳过；第10例真实 Redis 验收已另外运行。`release-contract`、正式 v1.4.4 检查与 `web-dist-sync` 在干净实现提交上通过；最终文档提交还须在合入后的干净副本重跑正式门禁。

```bash
CORE_TEST_REDIS_ADDR=<独占Redis> CORE_TEST_LIFECYCLE_PAUSE_REDIS=1 GOWORK=off go test -p 1 -race ./pkg/server/mq ./pkg/server/event ./pkg/server/observability -count=1 -json -timeout=3m
CORE_TEST_SHARED_FULL_LEASE=1 CORE_TEST_REDIS_ADDR=<独占Redis> GOWORK=off go test -p 1 -race ./pkg/server/event -run '^TestSharedKeyReliableHardCrashAndFullLeaseRecovery$' -count=1 -v -timeout=4m
CORE_TEST_REDIS_ADDR=<独占Redis> GOWORK=off go test -p 1 -race ./examples/10-reliable-multi-instance/... ./examples/integration/10-reliable-multi-instance -count=1 -v -timeout=4m
```

真实 TCP 代理断开、旧 owner 迟到 ACK、pending 恢复、新消息顺序、成功 ACK 未知、取消/超时等待与并发/预取限制分别有测试。网络场景加速单 key TTL 是故障注入，不取代上述原生租约测试。ACK 未知为真实命令执行后客户端 hook 返回错误，不代表全部网络故障已穷举。主 Agent 自审，未进行子 Agent 或外部独立审计。
