# 从 v1.3.0 升级 Core

适用基线为 `v1.3.0`（`7cdf8d998d9ac54a9e880736284536d27380838b`），候选版本为 `v1.4.0`。候选提交、门禁结果及未验证项见[发布准备记录](RELEASE_PREPARATION_2026-10-19.md)。本文不把历史版本的 Socket、Casdoor、内部通知协议迁移重复列成本次新增要求；从更早版本升级须同时阅读对应版本说明。

**当前候选尚不能正式发布：** 固定提交全仓回归中，07 的 WebSocket 场景在 ready 已返回 200 后首次下单得到 500，须先查清原因、修复并重新验证。Core 通过 `go:embed` 使用已提交的 `pkg/server/run/dist`，普通 Go 构建和运行不需要获取 `web/admin` 源码。该子模块的精确提交远端获取失败仅影响源码维护、重建和独立源码部署，不作为 Core 内嵌产物发布阻断；不要让其他项目在功能回归问题处理前按 `main` 自动升级。

## 必须检查的项目

| 使用方式 | 升级前必须处理 | 不需要的操作 |
| --- | --- | --- |
| 依赖缺省 MQ 自动连接 | 在每个实际使用 MQ 的服务 `etc/<service>.json` 显式设置 `MQ.Mode`、Provider、Usage 和 Broker 连接；生产可靠跨进程事件建议使用 `on`，连接失败拒绝启动 | 不为所有服务统一开启 MQ；不依赖系统 `etc/server.json` 替业务服务启用 |
| 使用 Badger pending、authstate 或 L2 | 停写并备份每个物理目录，在副本上验证 v4.9.6 的打开、重开、数据与回退；必须保留原路径和事实 | 不清库、不删除 LOCK、不把 pending 或撤销事实当缓存重建 |
| 多套 MySQL 账号或驱动配置 | 检查每个账号的真实库表权限及连接数预算；不同认证/驱动语义现在独立建池 | 不依赖其他账号先创建的池，不持久化或解析 `GetSyncPoolKey` 返回值 |
| 自定义元数据枚举调用 `InitRequest.NewID()` | 移走真实主键生成，改用已初始化的 `ServiceContext.NewID()`；元数据枚举不生成业务 ID | 不补另一套包级备用生成器 |
| 复制了 07 的规则读取实现 | 合入每次读取共享权威规则的修复，验证管理更新后下一次校验生效、读取失败拒绝 | 不再依赖永久正向缓存或手动调用 `Invalidate()` |
| 使用角色权限勾选树 | 更新后台及配套内嵌产物，保存后重开检查回显，并测试超过 500 条的完整撤权 | 不重新创建管理员、角色或权限表；不清除原授权数据 |

Go 最低工具链仍为 `1.26.6`，不是本轮新增要求。直接依赖变更为 go-zero `v1.10.2 → v1.10.3`、Badger `v3.2103.5 → v4.9.6`；传递依赖随 `go.mod/go.sum` 更新。消费方应重新解析依赖并编译，而不是仅替换旧二进制。

## MQ 与进程内事件

未配置或空 `MQ.Mode` 从 `auto` 改为 `off`；只填写 Broker 地址不会开启 MQ。已经显式保存的 `auto/on` 不会被覆盖；旧版本自动生成了 `auto`、但实际不需要 MQ 的服务，应改为 `off`。

下面是需要跨进程事件的业务服务配置片段，地址应替换成项目自己的 Broker：

```json
{
  "MQ": {
    "Mode": "on",
    "Provider": "redis-stream",
    "Usage": ["event-stream"],
    "RedisStream": {"Addr": "redis:6379"}
  }
}
```

`auto` 允许 Broker 不可用时降级；不能把进程启动成功当作跨进程可靠消息已启用。共享撤销、跨节点事件等有外部能力要求的路径仍按自身校验拒绝不可用配置。

**不使用 MQ 时，进程内 EventStream 和 ServiceEventBridge 仍会创建，可正常注册、订阅和发布。** 外部 MQBridge/Provider 未启用，不等于内存事件中心被关闭。仍用 `SubscribeEvent`、`NewEventPublisher(subject).Publish` 和框架 Outbox 组合入口；不要为无 MQ 场景另写事件总线。当前本地投递以服务自己的 Stream 为边界，不能据此宣称多个 ServiceContext 已无 MQ 自动互通；该历史缺口见[示例审查 P1-05](EXAMPLES_IMPLEMENTATION_REVIEW_2026-10-05.md)。进程内投递也不承诺进程崩溃后重放。

## Badger 数据与错误兼容

Core 的公开 Badger 适配方法没有新增原生 `*badger.DB/Txn` 参数或返回值。使用 Core 抽象的代码不需要把业务模型改成另一套类型；自行直接使用 Badger 的项目需独立检查自身 import、选项、工具及模块依赖，Core 升级不会自动迁移它们。

`BadgerDB` / `PrefixedBadgerDB` 返回的底层错误来自 v4。消费方若直接比较 `badger/v3.ErrKeyNotFound` 等原生 sentinel，须改用 v4 的对应错误并回归；Go API 签名检查不能发现这种运行时错误身份变化。不要仅因 Core 是 MINOR 就假定原生存储格式和错误对象完全兼容。

迁移顺序：

1. 停准入、停止写入与后台同步，确认没有进程继续打开目录；记录每个物理库、pending/Outbox 计数、关键事实摘要、有效 Options 和版本。
2. 保留完整原件，只在隔离副本尝试 v4 打开、查询、关闭及重开；核对最新值、删除记录、TTL、pending 和 authstate。人工普通/加密夹具的固定版本兼容实验已有[证据](BADGER_QUEUE_REPRO_2026-10-19.md)，不代替项目自己的存量卷验证。
3. 在隔离环境验证业务确认、远端写入/发布、重复确认及重启恢复，再切换正式流量。可靠写继续要求 `SyncWrites=true`、冲突检测和损坏 `fail`；不要顺便采用缓存配置。
4. 新版本尚未接收新事实时，可停新进程后恢复原件与旧版本；新版本已接单后，必须同时保全新增事实。先停止写入，由新版本做 Backup，在新目录用旧版本 Load 并核对后再回退；不能直接恢复旧快照，也不能默认让 v3 打开 v4 已写过的目录。

原生错误比较的源码盘点可从以下搜索开始，再结合项目自己的封装检查：

```bash
rg 'badger/v3|badger\.(Err|Options|DB|Txn)' --glob '*.go'
```

Core 没有自动清库或生产卷迁移工具。没有通过副本恢复验证的项目，应继续锁定原版本。参数与内存预算见[Badger 配置规范](../ai/core-skill/badger-configuration.md)，不存在所有服务通用的“最优参数”。

## 稳定实例身份是独立的启用步骤

只更新依赖不会自动启用稳定身份或注册自愈。`Cluster.IdentityMode` 缺省仍为 `legacy`，旧接口和发现配置保留。需要该能力时再按[稳定实例身份指南](STABLE_INSTANCE_IDENTITY_GUIDE.md)迁移：

- 注册键为服务名 + 持久 InstanceID，MachineID/实际 WorkerID 在独立编号权威持久绑定；重注册不重新编号。
- 每个副本有独占持久身份卷，编号 Namespace、Epoch 和权威账本有明确备份与恢复责任。不能克隆同一身份卷并行运行，也不能在权威丢失后重新初始化空账本。
- 盘点所有仍运行的 legacy worker，核对实际六位 WorkerID 与历史时间上界，停机隔离后 import；不能把自动编号容量解释成 1024 个 worker。
- 本地编号权威仅供显式开发环境；生产使用独立 Redis/etcd 编号权威，连接配置不继承发现配置，账本不挂发现 TTL。Consul 不支持 stable。
- 普通断网会撤销准入，恢复并读回确认后继续；持久 owner 冲突/账本丢失会终止服务。硬崩溃后须隔离旧进程并显式 recover，不根据发现 TTL 强行抢占。
- `/api/health` 为存活，`/api/ready` 为本进程准入。HTTP、同进程调用、gRPC 内部分发、受管理订阅与 Outbox 都检查准入；自行直连数据库的后台写入由项目调用 `CheckServiceAdmission()`。
- 注册 fencing 不取消已经发出的 SQL/MQ；换主前仍须外部隔离旧进程。回滚须停掉 stable 进程，保留身份、编号账本与业务卷，禁止旧/新二进制以同一身份混跑。

## 事务消息与查询的新入口

- `pkg/persistence/message` 与 `ITransactionDB` 当前为 Experimental 可选事务组合能力，提供 `Run`、`ConsumeInboxWith`、`ConfirmPublishedWith`；原 `IDataAction` 接口没有新增必选方法。仅已初始化的 MySQL/SQLite 事务支持该 SQL 能力，不能用 `GetRunDB` 冒充事务连接。
- 是否独立建 Outbox/Inbox、复用业务投递状态或流水、如何保存多目标状态，**先与业务使用者确认**；不要求所有项目新建技术表或迁移现有消息数据。业务事实与投递意图同事务，消费副作用与消费依据同事务；MQ 发布确认不等于消费者业务完成，失败/提交结果未知不能盲目重放写入。
- `UseOutboxWithOptions` 的 `BatchSize` 为加性设置，非正值继续默认 100，`KeyConcurrency` 默认 1。每满批成功后可继续排空，100ms 不是每秒只能扫描十批的硬限速。调大不代表容量达标；保持 earliest-first、同 key 失败屏障和确认原子性。
- `SearchItem.Context` 可把取消传入 MySQL/SQLite 普通、免 COUNT 及统计查询，nil 保持原行为，JSON 不接受或输出该字段。它不承诺初始建连、其他存储适配器或整个业务写事务可取消。复制了旧 07 `LoadPending` 的项目应传入真实 ctx，保留 `IDataAction.Load` 的只读连接恢复。
- MySQL 池故障恢复区分坏物理连接与整池关闭，只恢复无副作用读取；连接错误或超时后的业务写入仍需查权威结果及业务幂等，不能把返回失败当成没有落库。
- `InterpolateParams` 默认关闭；显式启用仅支持已验证的 utf8mb4。07 的插值与空闲连接 20 是示例覆盖，不是 Core 全局默认或所有项目的建议值。

## 管理端与示例

本轮修复 v1.3 RBAC 页面缺失，权限树保存按完整勾选集事务替换；内部读写 API 继续鉴权，但不暴露为页面按钮。升级后重启服务，在菜单管理执行“更新菜单”并刷新页面；自定义角色新增保持 `explicit` 策略。TestToken 仅用于开发测试，不创建真实管理员，也不消耗首位 Casdoor 管理员名额。真实管理员引导、角色域隔离规则沿用 v1.3.0。

直接用 Core 内嵌后台的项目随新二进制更新，无需拉取前端源码；独立提供静态文件时也可使用已提交的配套 dist，版本见 `pkg/server/run/dist/build-info.json`，不要只更新后台而继续服务旧静态文件。只有需要修改或重新构建 `web/admin` 源码时，才需解决对应 gitlink 的远端可获取性，再按精确提交检出；不能用后台远端 `main` 或 `git submodule update --remote` 代替版本锁定。独立 `web/scaffold-vue` 研究与 WIP 不属于本轮发布。

07 规则修复增加逐次权威 SQL 读取，旧缓存版本的性能成绩不能代表新代码。用户 facade 的幂等/去重集合长期增长尚未定义持久权威与保留期；原生负数 pending 的历史产生根因仍未复现。不要通过自动 TTL、截零或清 pending 掩盖这些边界。08 清空种子明细后搜索自动重建是保留的演示行为，不是需要升级修复的框架缺陷。

01～05 的监听前存储初始化、04/07 资源绑定时序、Manage Add Hook 错误传播，以及 08 父子事务/子行归属与复制问题仍在[原示例审查](EXAMPLES_IMPLEMENTATION_REVIEW_2026-10-05.md)中开放；本轮没有改动相应生产实现，不能因现有测试通过而将这些发现关闭。消费方不得原样复制有上述缺口的示例作为生产实现。07 支付状态与支付幂等属于应用业务规则，生产项目须自行定义和验收，不由 Core 内置订单状态机。现行存储要求是由组合根在监听前明确调用 `models.EnsureStorage()`；可选服务初始化 Hook 仍是方案，Core 尚未实现，不能只增加服务同名方法就假定框架会调用。

## 消费方升级验收

先在隔离检出或测试分支锁定实际候选精确提交；正式发布后再锁定 tag。不要把移动分支写入生产依赖。重新运行 `scripts/link-consumer-skill.sh`，让 AI 读取当前 `docs/ai/core-skill/`，而不是保留旧规范副本。

每个项目至少完成：

1. 编译及自己的 API/配置 smoke；逐项核对缺省 MQ 和真实数据库账号，不连接其他项目的测试库。
2. 进程内事件在 MQ off 下可用；需要 MQ 的项目另验证 Broker 确认、订阅失败不 ACK、重投幂等及自身消息回收策略。
3. 使用本地可靠写的项目核对旧卷副本重开、实际积压崩溃恢复与远端事实；不得用计数相等代替关键事实核对。
4. Manage 真实登录、角色关系、更新菜单、权限增减后下一请求的 403/允许行为；大量权限须验证跨页回显与撤权。
5. 只有启用 stable 的项目才增加断网超过 TTL、身份/编号不变、恢复真实内部调用、硬崩溃 recover 和退出不复活验收。
6. 登记消费方提交、Core 精确提交、配置指纹与结果；未运行的部分写 `NOT_RUN`。Core 本仓库门禁不能代替消费方部署或生产验收。

容量 `2000/s × 600s` 仍未达标，本次不继续压测，也不以功能/排空通过宣称性能达标。Bitzoom 等生产消费方未在本轮修改、重启或迁移。
