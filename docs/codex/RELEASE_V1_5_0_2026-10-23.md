# v1.5.0：有界失败处置与可靠交接验收

## 版本与范围

本轮以 v1.4.8（`c253fc9bcfa17a4d2d77be09d718f888bf8e1dd5`）为基线。部分成功仍全 store 退避及确认计数遗漏已在该基线修复，本轮保留真实自动 worker 回归，没有将其伪装为新发现。新增可选正式 API、配置和持久状态，按 SemVer 发布 MINOR v1.5.0；实际发布提交以正式 tag 为准。

Core 能力提交：`dce31428330fe7cb959c0c58523faad0f406279d`。示例与文档单独提交。没有修改 Bitzoom、Full-E4、Redis Provider、WS、归属、依赖或前端。既有前端 WIP 未纳入。

## 根因与实现

旧模式只执行 target 的条件确认，没有有限的逐原版本尝试预算、应用失败决策、持久接管回执与分组暂停调度。原索引前缀若全部失败，也没有跨组公平准入合同。仅修部分成功的调度条件无法补齐这些能力。

新增模式显式启用，沿用原 store、pending、syncExecMu、自动 worker 和生命周期。应用声明有限预算、分组及结果确认，Core 在每次执行前持久预占预算，结果未知先交应用，不能盲重放。应用必须先独立持久提交回执，Core 才结束技术投递；`HandedOff` 与 `IsSynced` 分开，接管不计业务成功、不自动释放同组屏障。

## RED 与原始证据

原件位于 [证据目录](evidence/writebehind-disposition-20261023/commands.json)。每轮命令、退出码、时长及原输出 SHA 均已保留；日志以无损 gzip 保存，`manifest.json` 核对压缩文件，`source-binding.json` 绑定最终 19 个 Go 文件。解压字节必须与 commands 中 raw_sha256 一致，不修改失败断言或原始输出。

- `api-red-final`：新正式 API 不存在的编译 RED；不是旧版本承诺已有该能力。
- `boundary-red`：重复接管不幂等、旧入口绕过新模式、历史 pending 盲调 target。
- `concurrency-red`：并发本地准入的真实 Badger 元数据事务冲突。
- `batch-snapshot-red` / `full-snapshot-red`：缺完整同批失败范围/原版本快照。
- `active-handler-red`：人工重试越过未实际退出的回调。
- `close-timeout-red`：技术 pending 为零掩盖实际回调未退出。
- `handoff-fact-red`：技术接管错误标为远端同步成功。
- `nil-compat-red`：新模式查询在 nil target 校验之前导致原零值错误契约回退。

以上均有对应 GREEN；它们记录新实现迭代时暴露的缺口，不声称 v1.4.8 已含这些 API。`api-red` / `example-api-red` 夹具准备阶段含模型/接线编译错误，`first-green` 含实现编译错误，单独保留，不能当运行时故障证据。第一轮 `nosql-race-first` 没有数据竞争报告，而是既有测试先观察 pending 清零、后观察 deferred metrics 的窗口：保持最终期望 8 不变，等待两项事实后验证；后续 race 均通过。

| 部分确认保留 error、零进展退避、旧消费者 | v1.4.8 原自动 worker、真实 Badger 及本地版本确认用例通过 |

| 07 正式接入 | `TestOrderDurableFailureHandoff` 和 `TestOrderFailureServiceContextLifecycle`：真实订单 store、独立接管库及正式资源链 |

## 兼容性、接入与未验证项

正式签名、配置和迁移见 [接入指南](WRITE_BEHIND_FAILURE_DISPOSITION_GUIDE.md)。默认 nil 不启用新模式；旧 target 无新增必选方法，旧模式仍可能按其原语义持续重试，不能宣称所有现有消费者都已有限。应用在组合根显式配置 policy、稳定 StoreID、纯函数分组和独立持久 handler，接受请求前绑定；I/O 须遵守取消并自行幂等。

新模式冻结 policy 和持久状态，旧绑定入口拒绝绕过；**不能用旧 Core 打开已启用新模式的原卷**。修改预算、分组或处置语义须停止实际在途工作并制定显式迁移，不删 mode 或 pending。历史 pending 初次启用先 Unknown，旧历史执行次数未知。应用负责外部事务真实提交的证明，Core 无法独立证明任意外部数据库 commit。

顺序作用域仅本 store 持久准入顺序，不承诺跨副本或业务全局序号。target 仍原串行批次，不合作代码不能强杀；失败回调实际占槽期间同组仍阻塞。技术 handoff 不等于业务 APPLIED；应用明确 Release 前组屏障保留。历史原件、成功生命周期和回执不自动清理，长期磁盘增长需应用容量预算，不能删 pending 换排空。指标显式扫描未解决索引，内存恒定但耗时 O(N)，不应高频调用。

NOT_RUN：外部真实 MySQL 事务/网络故障、完整 HTTP 示例/UAT、持续容量压测、物理断电或介质损坏、Bitzoom 接入/升级/部署、Full-E4。硬 kill 测试不能替代物理断电验证。仓库禁止子 Agent，本轮由主 Agent 完成代码与五轴自审，未进行独立外部审计。Core 本地验证不代表 Bitzoom 金融功能、UAT 或容量通过。
