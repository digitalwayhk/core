# v1.6.4：有界write-behind选批范围与重复工作修复

## 变化

后台selectDispositionRound与前台Save仍复用原FIFO。本补丁限定target/group/具体组queue的底层IteratorOptions.Prefix；进一步以既有mode的提交版本复用target范围，成员/相关状态变更与失效原子提交，绑定返回前完成冷核验。选中快照等BatchID就绪后同事务只写一次；cursor未变化时不重复写。原件、版本、指纹、前序、attempt、组屏障与批次身份核验均保留。没有新增提交器、队列、配置、格式或业务特例。

仅Prefix的实测不够，故没有在编译通过后结束。完整根因、五类真实RED、普通/race/多轮分段、原始证据位置及所有限制见[修复报告](WRITE_BEHIND_SELECTION_CONTENTION_2026-10-31.md)和[逐轮指标](evidence/writebehind-selection-20261031/metrics.json)。

## 实测结论及未解决项

- 同资源Linux历史场景，含队列的选批轮次平均17.19–17.49ms降至7.83–9.01ms；诊断覆盖中Save排队与选批重叠P99从12.579ms降至4.278ms。两种指标不是同一分位数，不混算。
- **整体Save P99没有一致改善，性能未全面验收。** Linux历史场景旧150.30–155.34ms、候选144.56–170.54ms；Mac有一轮18.06秒最大Save的未解释异常，原件保留。不保证任意机器的固定延迟，也不宣称解释或解决现场70.847ms旧请求。
- 当前源码完整nosql+04/07普通及race最终轮各478条PASS记录、53条SKIP，DATA RACE报告0；persistence/config/performance/release候选/web-dist/logging门禁通过。默认性能测试SKIP不算性能通过，显式窗口另有原件。
- 既有Badger硬杀恢复`Create a new file`错误仍存在：旧算法和候选独立20轮各17PASS/3FAIL（命令退出1）。后续单轮PASS不抹去这个FAIL；本补丁未修改或修复该问题。
- 新PID原卷恢复和旧→新、新→旧离线兼容已执行；暂停/未知/有限预算/接管屏障及IsSyncAfterDelete原版本保护保持。物理断电、长期容量、消费方升级/UAT/Full-E4同档复测NOT_RUN。

## 消费方升级与skill

在消费方自己的维护流程执行（Core本轮未替消费方执行）：

```bash
rtk proxy go get github.com/digitalwayhk/core@v1.6.4
rtk proxy go mod tidy
rtk proxy go list -m github.com/digitalwayhk/core
```

无需新增开关、改API或重新建库。继续可靠配置SyncWrites=true、DetectConflicts=true和既有预算/1ms窗口；不要通过清pending/历史、关刷盘、重启重置背压或扩大容量掩盖问题。普通/legacy写路径默认行为不变。

**skill需要同步。** 权威`docs/ai/core-skill/write-path-and-performance.md`与`testing-and-release.md`已经更新，说明精确范围、mode版本缓存、冷查、原子写集及未全面通过的性能边界；两个正式指南和04/07 README同步。`go get`不会自动更新消费方复制的skill，指向旧模块目录的软链也需重建。在消费方根目录执行：

```bash
rtk proxy bash -c 'core_skill_root=$(go list -m -f "{{.Dir}}" github.com/digitalwayhk/core); bash "$core_skill_root/scripts/link-consumer-skill.sh" --target "$PWD"'
```

使用复制模式的消费方加`--mode copy`，不覆盖消费方已有业务规则；再核对链接/复制来源为v1.6.4。普通`go get`消费已提交的内嵌前端，不要求下载前端源码子模块。

## 原卷与回退

StoreID、policy指纹、mode原字节及所有磁盘key不变；只是利用Badger自身提交版本作缓存代际。存量卷按原身份/policy绑定，启动重建缓存，未解决前序不被跳过；target作用域变更后仍有一次冷扫描，首次绑定可能增加启动准备时间。损坏marker明确报错，不当成空范围。

旧→新、新→旧的Core合成卷独立进程核验不代表允许两个进程同时打开同卷；应先真实停止target/handler及关闭卷。低于有界处置支持版本的旧二进制仍不能直接打开有界状态，不能删mode/pending或历史绕过。确认成功与物理本地回收不同，内存清理队列仍不提供跨重启补删旧已确认残留。
