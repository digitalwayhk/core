### 原生长窗：确认事实没有丢失，但参考实现存在恢复漏洞

原生长窗最终内存 pending 为42057，原检查点副本重开后有49277条派生索引和47173份本地事实，其中2104条索引找不到对应数据、5116份事实已经存在远端。逐键核验：42030个尚未进入MySQL的确认请求全部存在于本地，OrderID一致；确认请求在远端与本地同时缺失为0。不能把“尚未远端汇合”写成持久丢失。

阻断点确定为原生 `pending.batch` 对首条 `Key not found` 整批返回，持续重试同一个残留索引，挡住后续数据。这是本轮参考实现的恢复漏洞，不是 go-zero 缺陷。残留索引具体产生时序尚未复现，不推断为 Badger 库缺陷。

修正只作用于独立参考实现：派生索引缺少本地数据时，先核验匹配的远端订单、原 UserID/RequestID 哈希键与创建事件 Outbox，再清理索引；没有证明则保留并报错。pending计数以实际本地事实为准，ACK校验当前事实ID和请求指纹，重复确认不扣减其他记录。确定性 RED/GREEN、拒绝错误归属及 race 已通过。

原MySQL卷、Badger检查点保持不变。在独立MySQL物理克隆与Badger副本上，47173份本地事实全部完成幂等汇合，pending归零；克隆订单/Outbox均为708369，其中42057条新Outbox未发布。此验证只证明SQL及Outbox恢复，没有运行该副本的MQ发布/消费，不能冒充完整投递通过。

同时发现原生进程的清理回调早于外层日志复制，导致原生长窗应用日志未保留。已把日志复制移到原生StopProcess之后、删除目录之前。此证据缺口明确保留，不能将缺少日志解释为零错误。后续重跑单独记录新源码与结果，不改写f689b30测量。

### 已确认开销与专项建议

1. **连接池等待与复用。** 原生长窗已观察到order池20个连接全占用及大量累计WaitDuration；累计等待是并发请求等待之和，不能当壁钟。两边都使用open20/idle5。中途原生快照累计Connections为30715，Core快照为24945，Aborted_connects均0。先补齐WaitCount/WaitDuration/MaxIdleClosed/最大在用数，单变量比较idle容量与读写隔离；不能仅据累计建连次数就宣称唯一原因是idle5，也不直接全局增大池。
2. **每条参数化SQL临时prepare。** Core与原生GORM均`PrepareStmt=false`，DSN未启用driver interpolation。原生快照prepare/execute/close分别963361/963354/963347；Core为1175753/1175753/1175752。不是“三次SQL”或“三次往返”：确认的是临时prepare/execute/close协议命令，带来额外prepare往返及关闭命令。后续分别测试有界预编译复用或驱动参数插值，并验证参数/字符集、错误及事务兼容；不同时修改多个选项伪造因果。
3. **缺少默认规则记录的热路径。** 当前夹具没有持久默认规则；两边都按现有业务保留“未配置时回退默认且不缓存”，因此每次新下单都读规则，再查远端幂等。可对照测试显式配置相同默认规则或带变更失效的缓存；不能擅自改变管理员新增规则的生效语义。禁用规则被查询过滤后也会回退默认，应由业务确认“禁用配置”还是“禁止下单”的含义，不直接标成框架缺陷。
4. **发布前积压更大。** 两边长窗SQL unpublished约18–19万，而Broker lag/PEL只有几十。优先拆测远端同步、Outbox加载、XADD、发布确认、池等待和存储I/O；当前不支持先把问题归因消费并发。
5. **全量观测成本。** 原采样每秒执行订单COUNT及Outbox COUNT/SUM，数据库与Redis统计共用3秒预算。Core50项正式采样错误导致提前停发，观测为Partial；原生0项错误不能代表其恢复通过。应按阶段标注耗时、隔离统计预算并保留最终逐键核验，不能仅增加超时或放宽守护判通过。
6. **超时结果未知。** 两边内部接单路径保留已接受后继续处理的语义。失败但落库必须单列，调用方使用同一幂等键查询/重试；不得换新ID补单，也不得假设HTTP失败等于事务回滚。
7. **包导入触发全局清理及强制GC。** `pkg/persistence/database/oltp/connection.go:234` 的init启动5分钟周期任务；`performSmartGC`可能显式GC，`logCleanupStats`无条件调用`runtime.GC()`。压测发送器也导入Core，日志中在表缓存/DB连接为0时仍出现清理与GC统计。确认的是非业务显式启动的全局行为及潜在测量干扰，尚无单变量证据证明某个延迟尖峰由此造成。建议取消统计入口强制GC，把后台生命周期收归显式资源管理，并隔离负载生成器；当前不改基线或将其直接认定为唯一瓶颈。

当前可得结论：Core方案存在额外成本，原生方案也遇到共同的数据库/消息链路容量问题；本轮没有证明唯一瓶颈，更没有证明“更换HTTP框架即可解决”。原生恢复漏洞修正后的完整压力复验另列，不混用版本。

### 对照实现审查发现：Snowflake 低位取模造成通道偏斜

原生实现最初直接以 `OrderID % 4/8` 分配发布/消费通道。第三轮60,000个订单的发布通道分布为29,271/25,543/4,418/768；消费通道分布为29,134/25,466/4,387/748/137/77/31/20。声明的并发上限相同，实际工作分布却不相同，因此这批结果不能用于公平比较。

这是本轮新增原生实现的问题，不能归因 Core 或 go-zero。确定性测试使用8,000个低位相同的 Snowflake 订单，旧算法分布为8,000/0/0/0，RED；改为完整订单键的 FNV-1a 稳定散列后通过4/8通道分布检查及 race。原始 RED、绿色回归、旧测量全部保留，当前窗口正常结束后，驱动在轮次边界因源码变更校验停止，没有硬杀正在写入的服务。

## 解释限制

Core 已使用 go-zero HTTP 和 zrpc 客户端；本次比较的是原生应用方案与 Core 标准方案的整体差异。原生不实现 Core 的注册自愈、身份账本、通用 pending 版本/墓碑、运行图和统计任务；zrpc 原生入站中间件与 Core 自管 grpc-go 不完全一致。原生使用更简单的本地数据布局；两者都保留 fsync、异步同步、SQL事务Outbox、消费去重及成功后 ACK。

当前负载没有支付、取消、后台管理、配置变化、列表缓存命中或活跃 WebSocket，原生没有复制这些能力。本次结果只适用于下单及订单创建事件路径；任何差异不能直接归因为 go-zero 引擎，也不能证明整个框架的替换收益。
