## 07 首单 500 的定位与修复

未修改源码的单次重跑可以通过，说明只重跑取得绿灯不足以关闭问题。在隔离的旧代码副本中，将本地订单存储绑定受控延迟 2 秒，ready 仍返回成功，首单稳定返回 500；诊断捕获到 `订单可靠写入存储不可用`，对应 `ErrOrderWriteStoreUnavailable`。旧代码在异步 `IStartService.Start()` 绑定 runtime，而 legacy 准入不会等待该绑定，确实存在接受请求早于必要资源就绪的窗口。原全仓失败日志未保存完整 cause；本轮通过受控实验确认并修复这一实际缺口。

修复增加可选 `types.IInitializeService.Initialize() error`，标准 WebServer 在配置校验后、任一 HTTP/gRPC 监听器构造前同步调用所有初始化钩子。错误或 panic、后续构造失败会反向调用已尝试初始化服务的 Stop，并关闭其托管资源。原 IService 不增加必选方法，旧 Start 仍异步调用，未接入服务不自动改变时序。

07 订单服务在 Initialize 中完成 models.EnsureStorage 和实例级 store 绑定；用户服务在 Initialize 中完成必要订阅。main 不再重复承担订单存储初始化。初始化不得等待本进程监听或尚未启动的下游服务；Stop 必须允许部分初始化及重复调用。已有同签名 Initialize 方法的消费方须核对升级后的调用行为。

修复后的隔离副本施加相同 2 秒延迟，原首单和 WebSocket 场景通过。生产代码与测试就绪探测没有增加 sleep、忽略错误或删减断言。

## 前端发布边界

`pkg/server/run/htmlserver.go` 使用 `//go:embed dist`；已提交的 `pkg/server/run/dist` 随 Go 二进制发布，普通构建与运行无需拉取或编译 web/admin。干净候选检出未拉取子模块源码，仍完成上述全仓构建和回归。前端精确提交远端获取失败只影响源码维护和重新构建，不能作为 Core 内嵌产物发布阻断；发布策略和权威 skill 已同步纠正。

## 保留的限制

- 本版不是性能容量认证；`2000/s × 600s` 仍未达标，本轮没有重新压测或调整 Outbox 默认批量。
- 历史负数 pending 的原始产生根因仍未复现；已验证计数保护不等于关闭历史根因。用户 facade 幂等/去重集合的保留期仍由业务确认，不擅自增加 TTL。
- 01～05 的历史启动接线、04 的资源绑定、Manage Add Hook 和 08 父子操作等未在本轮修复的发现仍保留；新增钩子不会自动修复未接入的示例。
- Docker compose/容量等显式开关用例以及未启用的故障注入仍按实际结果跳过。Bitzoom/futures 的升级、生产部署、存量卷兼容和主机断电耐久均不属于本次验收。
- 本轮仅使用独占、带任务标签且数据有界的 4 个临时依赖容器，MySQL 数据为 1 GiB tmpfs，Redis 32 MiB，etcd/NATS 各 128 MiB，不创建数据卷。结束后按精确 ID、名称和标签回收，不操作其他项目。
