# Core v1.6.2：有界本地确认与公平提交

## 版本与修复

基线 v1.6.1 / `46b7551bff0ee2d760993592e6f37519fd63e5a8`。兼容修复按PATCH发布；修复提交为 `63123e630988250a3af73ac2cb840bd2ad08b522` 、`bcc186ea81f792297fd47f70218585916d394ac1` 与 `8c959c2d45f576f8a7d41e0d143a7fc1dceb796a`，正式发布提交以annotated tag/GitHub Release为准，不覆盖已有tag。

原有界write-behind在target返回后逐条本地可靠确认，与前台争用同prefix元数据互斥及Badger提交资源；不是持该锁等待MySQL。改为ReliableWriteStore固定最多8项/约1MiB编码软预算的可靠块；直接PrefixedBadgerDB最多32项，瞬时空闲不放大facade块。实际事务过大二分，不重调target。仅提交成功后更新真实pending、确认、hook和失败通知。

有界ReliableWriteStore复用原BatchCommitter FIFO，SQL、target、HandleFailure仍在外；原storageMu、sequence/cursor/组首原子性保留。组索引维护复用不预取value的迭代器。Close唤醒满队列未接收前台请求、排空已接受前台，保留内部通道等待原后台，再结束提交器；接受不等于持久化，超时不等于业务停止。

不增加配置或业务协议，不修改policy/存储格式、依赖、Redis、WS或消费方。原绑定API、legacy/零值、有限重试、未知结果、暂停/接管/Release、顺序屏障及IsSyncAfterDelete边界保持。加性只读本地事务观测详见[同步指南](WRITE_BEHIND_SYNC_GUIDE.md#有界后台本地确认的提交预算)。

## 消费方升级

```bash
go get github.com/digitalwayhk/core@v1.6.2
```

继续原UseWriteBehindWithFailureHandler及相同StoreID/policy/身份目录，无需新显式配置、worker或临时提交器。不清mode/pending/history，不关SyncWrites/DetectConflicts，不用reset_cache或TTL。

原卷合成副本已验证：新进程恢复v1.6.1的2000个pending，无新Save；旧v1.6.1进程核对新版2000个已完成原件/历史，attempt=1，不重投target。只覆盖本组件合成模型，不能授权在线回滚生产金融卷。停稳target/handler、备份并验证业务卷副本后再决定回退；不能回到不识别有界状态的旧Core，也不能并发打开同一卷。

hook仍只在原版本真实本地确认后触发，旧结果不删新版本，false保留、后续true须自己的确认。清理队列仍仅内存，不承诺重启补删，旧已确认残留不因升级自动回收；确认、物理回收和业务成功是不同事实。

## 验证与性能边界

[完整根因、函数、RED/GREEN、命令、大小/摘要及结果](WRITE_BEHIND_BATCH_CONFIRMATION_2026-10-31.md)。直接prefix的128条真实事务从129降至5；正式ReliableWriteStore固定8项预算为17次（含选批）；FIFO与前台8项量子均保留原始RED。完整nosql、04/07普通/race（各437 PASS、50 SKIP、0 FAIL）及真实SIGKILL/新PID恢复、实际事务过大/Commit冲突/部分块成功通过；持久化、配置、性能、快速、安全、发布、内嵌前端和日志门禁分别取证。

同机macOS/APFS、GOMAXPROCS=1、Go内存软预算1GiB、SyncWrites=true、2028字节Gob、50并发，三模式各三短窗/三持续窗口，共756000次Save。后台开启2000笔：平均约6.5–6.6ms→4.41–4.60ms，实际本地事务约2083–2086→369；40000笔持续窗口P99约106–118ms→72–76ms，最终pending=0、错误=0。两个无后台控制组各卷保留2000个pending，不能写成同步收敛。

**性能未完全验收：** 仍有72–76ms尾部及部分P95回归，未证明所有独立60–70ms长尾消失；没有保证Save低于10ms，没有解释全部726ms下单延迟。持续样本是20秒、2000可合并状态key的组件实验，不是金融流水长期容量认证；不是1CPU/1GiB容器硬限。OS同步调用次数、纯fsync、I/O与限流未采集，不能用Badger事务猜测。

正式发布须在干净精确检出执行普通/race、CORE_RELEASE_VERSION=v1.6.2 release-check --release、release-contract及web-dist-sync；任一失败不发布。实际命令、退出码、精确提交、原始失败、逐轮性能及发布后官方Go代理核验放入Release附件。
