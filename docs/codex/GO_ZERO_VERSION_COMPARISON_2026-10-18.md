# 07 原生 go-zero 版本对照

## 问题与版本核验

用户要求检查此前go-zero版本是否落后，并验证新版是否改善下单容量。仓库`go.mod`固定为`github.com/zeromicro/go-zero v1.10.2`；2026-10-18现场查询Go模块代理的`@latest`及[官方最新发布](https://github.com/zeromicro/go-zero/releases/tag/v1.10.3)，均为`v1.10.3`。模块时间为2026-07-31 17:19:17 UTC。

官方发布说明包含FIFO增长策略、指针切片解码、字符串边界、Redis HELLO/熔断与客户端管理修正。逐文件比较下载的两个正式模块，`rest/`与`zrpc/`没有代码变化。原生订单示例直接使用go-redis管理Redis Streams，没有使用go-zero的Redis封装；当前实现没有调用此次改动的`collection.NewQueue`。因此不能仅根据这些变更宣称下单性能会提高，仍需实测。

## 比较方式

业务、发送器和测试源码固定为`1e796e7`，采用已修正恢复逻辑的原生三进程，不混入前一轮旧参考实现的恢复缺陷。使用独立`-modfile`，仓库原有`go.mod/go.sum`保持不变；所有子进程构建继承同一`GOFLAGS`，使用`-mod=readonly`防止运行时依赖漂移。二进制构建信息另存，核验实际go-zero版本。

两份有效模块图仅有下列版本变化：

| 模块 | 旧版 | 新版 |
| --- | --- | --- |
| github.com/zeromicro/go-zero | v1.10.2 | v1.10.3 |
| github.com/pelletier/go-toml/v2 | v2.3.1 | v2.4.3 |
| go.mongodb.org/mongo-driver/v2 | v2.6.0 | v2.8.0 |

MySQL、go-redis、Badger、GORM、gRPC和Go版本保持一致。这是正式模块及其最低依赖要求的升级对照，不强行覆盖新版声明的最低版本。

每轮使用新的专用MySQL/Redis容器，标签`core.task=gozero-version-20261018`；相同的MySQL open20/idle5、buffer128MiB与提交持久化设置、Redis AOF everysec、Badger SyncWrites=true、合批/同步/Outbox/消费参数。500/s预热10秒，2000/s主档30或600秒，512在途，HTTP5秒/RPC2秒。守护保持pending40000或连续3次观测失败停发，停载最多360秒排空；通过容量还要求无发送器丢弃、成功率至少99.9%、无观测缺失或守护、5秒内排空。

短窗交替顺序为旧→新、新→旧、旧→新，随后新→旧各一个600秒目标长窗。保留所有失败，不拿未发出的目标数量当实际处理量。环境是同一本机、非独占主机，其他项目负载可能带来波动；三组短窗和单组长窗不构成生产容量认证或统计显著性证明。

## 前置验证

- 新版原生认证、依赖独立性、业务RPC、本地队列重开/幂等、索引恢复/拒绝无证明清理、并发合批、重复ACK和分路测试通过，race通过。
- 新版`go test -p 1 ./examples/07-shop-order-scale/...`通过。
- 上述普通/race包测试中，真实MySQL事务与Redis ACK测试因未配置专用地址跳过；真实外部依赖闭环由本次压力轮次另外验证，不能把跳过写成通过。

### 两版共同暴露的本地状态异常

**本轮并未证明原生参考实现的队列状态在长压下稳定。** 最终负数pending不能截成0，也不能作为排空通过的依据。固定源码继续测完，没有在两版之间修补应用实现。

仅打开关闭后的Badger检查点副本扫描，原文件前后SHA256一致：

| 物理检查 | v1.10.2长窗 | v1.10.3长窗 |
| --- | ---: | ---: |
| 派生队列索引 | 0 | 0 |
| 本地事实 | 0 | 1785 |
| 原检查点哈希保持一致 | 是 | 是 |

新版的1785份本地事实没有对应派生索引。原MySQL保持停止，通过只读挂载复制其物理卷，在独立克隆上只做SELECT逐条核验：1785份均有相同ID、UserID、requestID及指纹的远端订单，均有匹配且已发布的OrderCreated Outbox；本地哈希键与身份匹配，远端缺失及身份不匹配均0。没有回放、补写、清理原库或原Badger。旧版物理记录已空但内存指标仍为负；这进一步说明指标不能替代物理扫描。

因此，已确认请求均已远端匹配，新版残留也已汇合，当前没有确认事实丢失证据；计数漂移及无索引本地残留的具体产生时序仍未确定，不能归因于go-zero、Badger或某项升级。两版都出现异常，说明它不是仅在新版出现的现象，也不证明两次异常一定同因。`pending.go`的计数、索引生命周期和`business.go`按depth读取本地列表需要专项复现后再处理，本轮不修改它们。

order日志中，两版均观察到本地背压及`invalid connection`，包括下单、同步、Outbox加载和发布确认阶段。新版下单路径1740次、同步6次；旧版分别4485次、12次。这些是保留日志中的事件次数，不等同于请求总失败数，尚未证明其与计数异常的因果。

证据目录为`.temp/gozero-version-20261018/`，逐轮参数、源码/依赖哈希、请求、采样、进程日志与分析在`comparison-v1/`；`retained-fact-verification.json`记录残留核验，`physical-v1.10.*-long.json`记录原始检查点保护。旁路每约57秒只读pending用于进度，准备期未采集不等于正式采样缺失；正式结论以原采样、逐键和物理核对为准。

## 结论与建议

仓库只落后最新稳定版一个补丁。v1.10.3可编译并通过本轮07包回归及原生定向race，但**升级没有解决本轮2000/s×600秒容量目标，也没有证明稳定优于v1.10.2**。新版短窗p99中位数更低，但完整短窗门槛仅2/3通过，旧版3/3；长窗两版均FAIL，并有参考实现的状态异常，不能据此认定引擎性能的因果或生产容量。

优先在检查点副本上复现计数/索引生命周期异常，并为“事实已远端汇合、本地物理状态、内存pending”分别建立不变量，再继续版本或SQL/连接池单变量容量对照。此前数据库连接复用、参数化SQL协议、缺省规则反复读取、发布前积压和全局统计GC的建议仍然有效，未因这次补丁升级得到解决。

本轮仅产出实验依赖文件与证据，不把v1.10.3自动设为Core默认依赖。正式升级还需要Core其余模块和消费方兼容性回归；本轮未运行这些检查。所有本轮原始容器、数据卷及验证克隆保留，测试结束后均停止。
