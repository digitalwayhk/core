# MySQL 50／100 连接差异诊断

## 结论与证据边界

状态：**Partial：已定位反复查库及连接池/通讯路径排队，原始单轮尖峰的唯一触发源未确定。**

原报告初筛的 MySQL50 P95=20.5 ms、MySQL100 P95=58.0 ms 没有稳定复现。追加诊断中排名多次反转；不能再据此推荐 50 优于 100，更不能据此认定 MySQL 在 100 连接时发生固定的内部竞争瓶颈。

具体查实了两个问题：

1. 初筛只有单轮、短窗口，应用连接池未预先建立全部连接，且宿主机/Docker 虚拟机共享资源没有隔离。配额只是上限，无法保证各轮获得相同的 CPU 调度和 IO 条件。单次尾延迟被过度用于选择“优选”档位，原先该推断撤回。
2. 压测夹具没有订单规则。现行代码在规则不存在时返回默认规则，明确不缓存此回退，因此每单都会额外执行一次规则查询事务，并以回滚结束；同时每单还有一次远程幂等查询事务。它放大连接占用和数据库通讯压力。通过真实 Manage 配置规则后，相应回滚消失，证明了该路径；但尖峰仍存在，因此它不是充分解释原始差值的唯一原因。

目前没有证据把原来 58 ms 那一轮唯一归因于某项 MySQL 参数、行锁、CPU 饱和、Go 调度或 Docker 端口转发。原始窗口没有保存足以还原这一瞬间的逐 SQL/网络/调度联合证据，不能用后续不同时间的实验替代该证据。

## 真实链路复现

继续使用分支 `feat/postgres-support`、HEAD `9f5d7d0372c985aac3b1b7abfd11cda60e3a85f4` 和既有 MySQL `core-tx-load-mysql-r2-20261018`。版本、4 CPU／6 GiB 上限、2 GiB buffer pool、200 服务端连接上限均保持；没有增加容器。每轮仍是 500/s × 2 秒、2,000/s × 6 秒，最多 512 在途，每轮唯一数据库及 pending 目录。

前四轮顺序为 50、100、100、50，读取实际应用池并每 200 ms 采集 MySQL；后两轮另采集应用运行时、阻塞栈和 CPU 剖面。服务端临时开启 `events_waits_current`、`events_statements_cpu`，其余 instrument 保留原值，结束后恢复为 NO。

| 诊断轮次 | 连接数 | HTTP P95 ms | 漏发 | HTTP 失败 | 累计池等待秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 50 | 956.60 | 4,638 | 5 | 2,678.67 |
| 2 | 100 | 614.75 | 1,646 | 1 | 1,647.25 |
| 3，带运行时剖面 | 100 | 481.51 | 798 | 0 | 1,708.94 |
| 4，带运行时剖面 | 50 | 754.15 | 3,132 | 1 | 2,568.87 |

这些轮次说明排队可复现、原来的排名不可稳定复现。存在漏发时各轮实际发送量不同，不能把排空时间直接当作公平的容量比较。采集有开销，不能与原初筛相减来计算性能变化。

四轮共确认 41,779 笔，确认 ID 丢失/错键均为 0；7 个失败响应对应订单后来已持久化，单独登记，没有当作确认丢失。最终各轮本地 pending、未发布 Outbox、消费组 lag/pending 均清零。前三轮观察到退出码 0；第四轮保留 PASS 日志及完整事实/ACK 核验，退出码未由控制器观察。控制器在第四轮 Go 测试自行结束后停止后续重复调度，没有终止活动 Go 测试。

## 排队定位

四轮均记录到以下增量为零：

- `Innodb_row_lock_waits`、`Innodb_row_lock_time`；
- `Innodb_buffer_pool_wait_free`；
- `Innodb_log_waits`；
- 容器 cgroup `nr_throttled`、`throttled_usec`。

这些指标不支持将本轮异常解释为行锁等待、等待空闲 buffer 页、redo log buffer 不足或该容器的 CPU 配额限流。**它们不等于排除了全部 IO 延迟、InnoDB 内部 mutex 或共享虚拟机调度竞争**；相关内部 mutex instrument 未全面开启。

应用阻塞栈主要落在规则读取、幂等查询的 `database/sql` 借连接、MySQL socket 收发，以及已可运行的 goroutine。没有发现该路径上的业务互斥锁形成主导阻塞。两份 20 秒 CPU 剖面中，`syscall.rawsyscalln` 平坦占比分别约 35.5%／37.1%，另有明显的 Go 调度和线程唤醒相关成本；GC 累计总停顿约 39.6／24.4 ms，不支持把数百毫秒尾延迟全部解释为 GC。

定位范围因此是**前台小事务的连接占用、通讯往返和运行时排队**，而不是已证明的单一数据库锁热点。池等待统计不是 SQL 行锁统计，也不是 SQL 服务端执行时间。池变大只能增加允许的并行访问，是否改善必须看相同条件下的负载测量。[Go 连接管理](https://go.dev/doc/database/manage-connections)

## 额外规则事务的代码与验证

现行代码链路：

- [OrderRuleCache.Get](../../examples/07-shop-order-scale/order-service/business/order_rule_cache.go)：缺规则时返回内建默认值，不缓存该回退；
- 同文件 `loadEnabledOrderRule`：通过 `models.RunRemoteTransaction` 查询规则；
- [runTransaction](../../examples/07-shop-order-scale/order-service/models/internal/store/local_store.go)：查询返回 `ErrOrderRuleNotFound` 时执行回滚；
- [LocalOrderWriter.Accept](../../examples/07-shop-order-scale/order-service/business/local_order_writer.go)：另行执行远程幂等检查。

不缓存默认回退是现行明确语义：管理员新增规则后，后续请求应能读取它。本次没有修改该生产行为，也没有关闭幂等或可靠写来换取性能。

第三轮确认 12,202 笔，对应轮末 SQL 摘要有约 24,631 次 START TRANSACTION、12,192 次 ROLLBACK；包含后台事务，不能把总数全部算成 HTTP 请求。通过真实 Manage 配置默认规则后：

| 测试数据/运行设置 | 连接数 | P95 ms | 漏发 | HTTP 失败 | 规则 miss 回滚 |
| --- | ---: | ---: | ---: | ---: | --- |
| 配置规则，原调度设置 | 50 | 472.01 | 712 | 0 | 消失 |
| 配置规则，原调度设置 | 100 | 26.28 | 0 | 0 | 消失 |
| 配置规则，GOMAXPROCS=4 | 50 | 344.01 | 440 | 0 | 消失 |
| 配置规则，GOMAXPROCS=4 | 100 | 51.71 | 0 | 0 | 消失 |

Go4 的 50 连接轮与本任务的一次短回归检查有重叠，保留证据但不用于性能归因。Go4 的 100 连接轮没有该重叠，实际运行时记录确认为 4，仍不能证明固定调度并发就能消除波动。上述对照均为单次诊断，不用于宣布最优参数。规则配置对照最终事实与 ACK 均核验通过。

## 最小只读 SQL 对照

另编译一个探针，去掉 HTTP、gRPC、Badger、同步写及 Outbox，只保留与前台类似的两次只读事务：默认规则 COUNT 后回滚、幂等键 COUNT 后提交。查询同一测试 schema，目标仍是 2,000 次操作/秒、6 秒，每操作包含两次事务。

1. **诊断开销**：关闭临时 SQL CPU/当前等待采集后，宿主机探针仍出现较大波动，所以这两个开关不是出现抖动的必要条件；不能据此说采集没有开销。
2. **协议往返**：对照默认预处理和 `interpolateParams=true`。驱动文档说明后者可减少 prepare/execute/close 往返；宿主机结果没有稳定一致的提升，故未将其认定为唯一原因，也未修改框架 DSN。[MySQL Go 驱动说明](https://github.com/go-sql-driver/mysql#interpolateparams)
3. **宿主机与容器**：相同探针分别在 macOS 宿主机通过发布端口，以及现有 MySQL 容器内通过 loopback 执行。顺序运行时容器通常更快；再做六组同时段配对，部分尖峰两边均出现。配对总负载为 4,000 次操作/秒，不能与单探针 2,000 次结果直接比较。该实验不支持把全部异常归咎于 Docker 端口转发。
4. **Go 调度并发**：探针以及完整链路分别限制 GOMAXPROCS。未获得足以证明它是唯一原因的稳定改善。
5. **冷连接**：先持有并建立全部连接后释放，再开始负载。各档冷/暖各两次，结果如下。

| 池上限 | 冷池 P95 两次，ms | 暖池 P95 两次，ms |
| --- | --- | --- |
| 50 | 9.89、10.13 | 7.74、8.44 |
| 100 | 11.78、9.98 | 8.16、20.20 |

预热能减少部分连接等待，但暖池 100 仍有波动，不能把原始差异全部归因于连接建立。最小探针同为 100 连接、同一 SQL/数据库/默认协议时，也曾出现 P95 约 9.98、96.33、360.38 ms 等不同样本；这些跨时段数据用于证明不稳定性，不作为可比的性能排名。

## 对原报告的修正

原始测量值保留，但撤回“50 是 MySQL 更优档位”的推断。原报告的候选复测只补测了 50，没有同等次数复测 100，存在选择偏差。后续数据库比较必须明确测试缺规则回退还是已有规则缓存命中，区分冷启动突发与连接已稳定建立的窗口，并对各档等量交替复测。

目前可以报告：**额外事务放大与前台连接排队已确认；原始单轮尖峰的唯一触发组件仍未确定。** 不将“CPU 配额一致”当作资源已隔离，不将“纯 SQL 也抖动”直接等同于“MySQL 引擎有问题”。
